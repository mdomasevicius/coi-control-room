# Control Room mod

A Captain of Industry mod that serves the Control Room dashboard ([web-src/](web-src)) from the game's own web API server
(`web_api_start`, `http://127.0.0.1:3073`). The page and the API share one origin, so no proxy, Docker or CORS
setting is needed.

| Route | Returns |
|---|---|
| `GET /control-room` | The dashboard (`index.html`) |
| `GET /control-room/{file}` | Top-level files of the build (`favicon.svg`) |
| `GET /control-room/assets/{file}` | Hashed JS, CSS and fonts (cached as immutable) |
| `GET /api/mods/control-room/hello` | Health-check JSON |
| `GET /api/mods/control-room/speed` | The faster speed the game offers above 3× (sandbox, or after `set_game_speed` 4–20): `{ superSpeed: N \| null }` |
| `GET /api/mods/control-room/unity` | Unity now: amount, cap, last month's net, per-category totals, this month's records |
| `GET /api/mods/control-room/unity/history` | Unity per category over time: `resolution` = `days` \| `months` (default) \| `years`, `count` = 1–1000 (default 24) |
| `GET /api/mods/control-room/electricity` | Electricity now (generated, consumed, demanded, capacity, wasted), period averages, per building type (kW) |
| `GET /api/mods/control-room/electricity/history` | Production, consumption and capacity over time, in total and per building type |
| `GET /api/mods/control-room/computing` | Computing now (produced, demanded, capacity), period averages, per building type (TFLOPS) |
| `GET /api/mods/control-room/computing/history` | Production, demand and capacity over time, in total and per building type |
| `GET /api/mods/control-room/population` | Population, housing, homeless, starving, workers, health and what changed it, disease, births and deaths, each settlement and its needs |
| `GET /api/mods/control-room/population/history` | Health gained and lost (in total and per category), people born and lost, over time |

All `/history` routes take the same `resolution` and `count` and start with the **newest** completed period.

## Unity routes

The game's `/api/v1` has no Unity data. These routes read the game's Unity manager, the same source as the
in-game Unity window. They run on the simulation stage, like the game's own read routes.

`/unity`:

```jsonc
{
  "quantity": 52,                  // Unity on hand, as the game UI shows it
  "cap": 500,                      // Unity cap
  "lastMonth": { "net": 12.5, "possibleNet": 15, "netWithOneTimeActions": -40 },
  "categories": [{
    "id": "UpointsCat_Health", "name": "Health", "icon": null,  // stats category; icon is a path or null
    "oneTimeAction": false, "ignoreInStats": false, "hidden": false,
    "generated": { "lastDay": 0, "lastMonth": 0, "thisYear": 0, "lastYear": 0, "lifetime": 0 },  // or null
    "consumed":  { "lastDay": 0, "lastMonth": 0, "thisYear": 0, "lastYear": 0, "lifetime": 0 }   // or null
  }],
  "thisMonth": [{                  // itemized, like the game's Unity tooltip
    "category": "…", "statsCategory": "…", "title": "Bread",
    "icon": "Product_Bread",       // product, building or edict with that name (for /api/v1/icons/{id}), or null
    "exchanged": 3, "max": 4, "possibleMax": 4  // e.g. generated 3 of a possible 4
  }]
}
```

`/unity/history` returns `{ resolution, count, categories: [{ id, name, icon, …flags, generated: number[] | null,
consumed: number[] | null }] }`. Each series starts with the **newest** completed period (checked: the first 12
months of a series sum to `lastYear`).

## Electricity, computing and population routes

Like Unity, these read the game's own managers (`ElectricityManager`, `ComputingManager`, `PopsHealthManager`,
`SettlementsManager`, `WorkersManager`), the sources of the in-game power, computing and population windows. The
managers are looked up per request, so a game version without one makes that route answer 404 instead of
breaking the mod.

- **Electricity** values are the game's raw `Electricity.Value` (kW). `now.generatedText` is the game's own
  formatting ("12.4 MW") to check the unit against. Period values are averages (the game's `ElectricityAvgStats`).
- **Computing** values are the raw `Computing.Value` (TFLOPS); `now.producedText` is the game's formatting.
- **Population**: percentages are percent (61.4 = 61.4%), and health gained/lost per category (`generated` /
  `consumed`) is in percentage points (checked against `health.lastMonthRecords`). `health.thisMonth` stays 0 until
  the month ends, so `lastMonth` is the current reading. Settlements have no id or name in the game, so they are
  numbered.

## Layout

```
manifest.json, ControlRoom.csproj   the mod
src/                             mod code (C#); WebRoutes.cs serves the dashboard
web-src/                         the dashboard: Svelte 5 + Vite app, see web-src/README.md
web/                             built dashboard (generated by `make web`, gitignored), embedded in ControlRoom.dll
```

`make web` runs `vite build --base=/control-room/` in `web-src/` and writes into `web/`. The .NET build embeds
everything in `web/` into `ControlRoom.dll`.

## Requirements

- .NET SDK 8 or newer (`dotnet`). Visual Studio and Unity are not needed.
- Node 22+ and pnpm, for the dashboard build.
- The game installed through Steam. The build compiles against its DLLs in
  `Captain of Industry_Data/Managed`, so no NuGet packages are needed.

## Build and install

```sh
make install      # build the dashboard, build the mod, copy it into the game's Mods folder
make deploy       # same, but builds first and swaps the whole mod folder in at once (nothing changes if a step fails)
make dev          # dashboard dev server with hot reload against the running game
make help         # all tasks
```

`make install` copies `manifest.json`, `ControlRoom.dll` and the PDB to `$COI_MODS/ControlRoom/`. `make dist` makes a
shareable `dist/ControlRoom_<version>.zip`.

| Variable | Default |
|---|---|
| `COI_ROOT` | `~/.local/share/Steam/steamapps/common/Captain of Industry` |
| `COI_MODS` | `~/.local/share/Steam/steamapps/compatdata/1594320/pfx/drive_c/users/steamuser/AppData/Roaming/Captain of Industry/Mods` (the game runs under Proton) |

## Test in game

1. Enable **Control Room** in the mod list: for a new game, or for an existing save (the manifest allows adding and
   removing the mod from saves).
2. Open the console and run `web_api_start isPersistent:true`. A persistent server starts by itself in every game on
   this machine (a global setting, not stored in the save) until you run `web_api_stop`.
3. `make routes`: the routes above should be listed. `make unity` prints the Unity stats.
4. `make open` opens <http://127.0.0.1:3073/control-room>.

`make log` shows the mod's and the web API's lines from the newest game log.

**New mod code needs a game restart.** Loading a save again isn't enough: the game caches loaded mods by id and
reuses an already-loaded DLL of the same name. `non_locking_dll_load` only lets `make install` overwrite the DLL
while the game runs.

For UI work, `make dev` (hot reload at http://localhost:5173, proxied to the running game) is faster than
reinstalling the mod; build the mod to ship.

## Release

1. Set `"version"` in `manifest.json` (and the game versions, if they changed), commit, push.
2. Tag that commit with the same version: `git tag 1.0.1`.
3. `make release DRY=1` builds the zip from the tag and shows the release notes; `make release` pushes the tag and
   publishes the GitHub release with `ControlRoom_<version>.zip` attached. It needs the game installed (the build
   references its DLLs) and the GitHub CLI logged in (`gh auth login`).
4. Upload the same zip to the mod portal by hand.
